SECTION 1: EXECUTIVE DATABASE SUMMARY
============================================================

Current database architecture:
- Supabase is used as a narrow backend for:
  - auth profile provisioning (DB trigger path)
  - metrics aggregation (user_daily_metrics)
  - storage backup bucket (chronospark-sync)
  - monetization domain (subscription/wallet/transactions/purchases/entitlements)
- Core planner entities (tasks/goals/routines/timeline/notes) are not persisted as first-class Supabase tables in active runtime flows.

Current persistence architecture:
- Local-first for core product entities.
- Core records are primarily persisted via Hive + SharedPreferences + SecureStore.
- Supabase is selectively used for cloud backup payloads and monetization state.

Supabase usage:
- Reads: monetization tables, user_daily_metrics.
- Writes: upsert into user_daily_metrics; storage uploads to bucket path uid/backup/*; RPC consume_monetization_credits.
- Realtime: stream on user_daily_metrics.

Local storage usage:
- Tasks: Hive JSON records.
- Goals: Hive JSON snapshot.
- Routines/Habits: Hive JSON snapshot.
- Timeline events: SharedPreferences JSON.
- Profile: SecureStore JSON.
- Settings: SharedPreferences JSON.
- Tutorial/onboarding/mission/workspace states: SharedPreferences and SecureStore.

Hybrid storage usage:
- BackupService + SyncService combines local snapshots and Supabase Storage object sync.
- user_daily_metrics is hybrid (local metric accumulation + Supabase upsert/reads).

Classification:
- Current state: Partially wired hybrid architecture.
- Not overengineered globally; some subsystems are intentionally narrow.
- Underengineered for cloud-native multi-tenant planner persistence (core planner domain missing first-class remote tables).

Verdict:
- KEEP: local-first robustness and monetization schema
- NORMALIZE: ownership and completion persistence model
- REFACTOR: creator/timeline -> DB flow boundaries
- SPLIT: analytics/derived data from canonical planner facts
- MERGE: routine/habit naming model and planner object contracts

SECTION 3: TABLE-BY-TABLE AUDIT
============================================================

A) public.user_daily_metrics
- purpose: per-user daily aggregate metrics for analytics/health/realtime.
- fields observed:
  - user_id, date, device_id, tasks_created, tasks_completed, momentum_peak, created_at, updated_at
- ownership model:
  - auth.uid scoped by RLS in secure migration; PK now (user_id, date)
- timestamps: created_at, updated_at
- relationships:
  - user_id -> auth.users(id)
- indexes implied/required:
  - existing: user_daily_metrics_device_date_idx
  - implied: (user_id, created_at) for chronology scans if used broadly
- RLS assumptions:
  - select own rows, insert own rows, update own rows
- risks:
  - security definer global metrics function exists; must be tightly controlled
  - conflict target in app uses device_id,date; schema PK moved to user_id,date (logical mismatch risk)
- missing fields:
  - event granularity fields if later needed for detailed analytics

B) public.profiles
- purpose: auth user profile extension mirror
