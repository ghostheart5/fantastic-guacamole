SECTION 1
EXECUTIVE INTEGRATION SUMMARY
============================================================
Current integration architecture:
- Core execution pipeline is local-first and provider-driven.
- Creator writes through state actions into local repositories, then mirrors into Timeline and Logs.
- Completion side effects fan out into Learning, Profile XP/Streak, SI refresh, Timeline reflection events, CompletionEvent local store, and analytics.
- SI Console consumes a broad aggregated model from tasks, goals, logs, timeline, memories, profile, trajectory, values, and soul map.
- Supabase is strongly used for monetization, selective health checks, cloud backup storage sync, and Firebase token bridge.
- Two monetization stacks co-exist (feature stack and legacy stack), now partially normalized by a compatibility adapter.

Intended integration architecture (per requested ecosystem):
- Creator is source of truth.
- Creator -> Timeline is canonical.
- Timeline + Completion feed Ascension, Future Vector, Smart Planner, and SI Console.
- Profile + Subscription establish account/system awareness.
- Supabase supports synchronized cross-device integration boundaries.

Major integration strengths:
- Explicit task and goal fan-out to Timeline and Logs.
- Event bus exists and invalidates dependent providers across task/goal/log/timeline/progression/memory/notification lifecycle events.
- SI aggregation centralizes many cross-system reads in one provider path.
- Completion pathways trigger multiple downstream effects consistently from task actions.
- Cloud sync queue and retry behavior provide resilience for sync-to-cloud actions.

Major integration weaknesses:
- Creator source-of-truth is split: tasks/goals are integrated, but routines/habits and memory/note semantics are fragmented.
- Timeline is mostly fed by mirrored reflection events, not a fully typed canonical event contract across all systems.
- Completion-to-intelligence is mostly inferred from logs and learning state, not from a first-class completion event stream consumed by all downstream systems.
- Profile, Settings, and Subscription remain partially coupled with duplicated access pathways.
- Supabase ownership is uneven: monetization is strongly integrated while creator/timeline/profile core data remains local-first with backup sync.

Most disconnected systems:
- Completion -> Smart Planner (direct typed completion feed is missing; mostly indirect via execution signals and trajectory).
- Settings -> SI Console (no direct settings visibility in SI aggregation).
- Subscription -> SI Console (no direct subscription state in SI aggregation).
- Creator memory/note intent -> memories subsystem (notes often become task-like entries rather than memory-native flows).

Most integrated systems:
- Creator <-> Task actions <-> Timeline <-> Logs.
- Task lifecycle <-> Profile progression/learning/SI refresh.
- SI Console <-> SI aggregation surfaces (tasks/goals/timeline/trajectory/values/soul map).
- Monetization feature stack <-> Supabase monetization tables + purchase verification flow.

Verdict:
- KEEP: task/goal -> timeline mirror backbone, event bus invalidation model, SI aggregation entrypoint
- MERGE: dual monetization stack call paths behind one app-facing integration contract
- REWIRE: completion event fan-out into explicit downstream consumers (Ascension/Future Vector/Planner)
- SIMPLIFY: profile/settings/subscription awareness via single account-state integration model
- UNKNOWN: full routine/habit semantic path and future-intelligence feedback loops under all edge states

Overall verdict: REWIRE

2) Creator
- Purpose: capture tasks/goals/milestones/notes/plans from user intent
- Source of truth: creator actions dispatch into task/goal systems
- Inputs: dynamic form data, voice handoff, mission bridge prompts
- Outputs: created entities, first-item flags, timeline/log side effects
- Dependencies: task actions, goals notifier, mission provider, app flow

3) Timeline
- Purpose: temporal/event layer for activity, risk, forecast, and history
- Source of truth: timeline repository + timeline notifier state

SECTION 4
CREATOR INTEGRATION AUDIT
============================================================
Trace:
Creator -> creator actions provider -> task/goals providers -> persistence -> timeline/log mirrors -> intelligence invalidation

After creating a task:
- Persisted via task usecase/repository.
- Immediately connected to timeline via connectTask.
- Mirrored to logs and timeline reflection.
- Task lifecycle event emitted on event bus.
- SI decision invalidated/refreshed.

After creating a routine:
- In creator flow, routine normalizes to habit semantics in task creation path.
- Separate routines provider exists with isolated repository path and no direct timeline fan-out.
- Integration is partial and split across task-like and routine-specific channels.

After creating a goal:
- Persisted via goals notifier/usecases.
- Fan-out adds mirrored log entry and timeline connectGoal.
- Goal lifecycle event emitted; profile progression increments.

After creating a note:
- Note can be transformed into TaskEntity (kind note) and then follows task flow.
- This reaches timeline/log/task pipelines, but may bypass memory-native pathways.

Systems receiving creator information now:
- Timeline, Logs, Profile progression, SI refresh/event bus, Tutorial mission state.

Systems that should receive but do not consistently:
- Smart Planner (direct structured creator payload feed not explicit)
- Future Vector (receives derived signals, not canonical creator record stream)
- Completion analytics as first-class creator-origin metadata
- Memory subsystem for note-native semantics

SECTION 14
DATA SYNC AUDIT
============================================================
Local -> remote sync:
- Supported via SyncService full backup and tasks-only backup upload to Supabase storage bucket path scoped by user.
- Includes queued retry through offline sync queue for failed sync actions.

Remote -> local sync:
- Supported via backup restore and task restore pathways.

Provider refresh paths:
- Event bus invalidates dependent providers for lifecycle changes.
- Task/goal/timeline/log actions explicitly invalidate key providers and SI decisions.
- Restore from cloud invalidates tasks, profile, goal progress, optimization config.

Stale state risks:
- Sync delta fallback behavior and partial cloud reachability can leave local and cloud snapshots diverged.
- Multiple parallel monetization stacks risk stale entitlement state if not uniformly consumed.

Duplicate state risks:
- Subscription/access state exists across feature monetization and legacy paywall tracks.
- Completion represented in task status, logs, timeline mirrors, and completion event repository without one authoritative event stream consumed everywhere.

SECTION 17
TOP 25 INTEGRATION RISKS
============================================================
Critical:
1) Dual monetization pathways can diverge entitlement behavior between legacy and feature stacks.
2) Completion is multi-represented (task state, logs, timeline mirror, completion repo) without one canonical downstream contract.
3) Smart Planner lacks direct structured completion + creator feed; planning guidance may lag real execution state.
4) Future Vector relies on derived signals rather than explicit completion and creator event contracts.
5) Sync model is snapshot-based and can produce cross-device divergence windows.

High:
6) Routines/habits integration is split from creator primary flow.
7) Notes can route into task semantics and bypass memory-native pathways.
8) SI aggregation does not include first-class subscription status.
9) SI aggregation does not include first-class settings state.
10) SI aggregation does not include explicit sync health/queue state.
11) Goal and task fan-out patterns are similar but not yet fully normalized via one integration contract.
12) Event bus invalidation can hide ordering/race assumptions under heavy async fan-out.
13) Timeline can contain mirrored reflection events that inflate signal interpretation.
14) Profile/account identity and subscription entitlement are not unified into one account-state model.
15) CompletionEvent repository is local-only and not guaranteed as intelligence input.

Medium:
16) Timeline event typing from mirrors may blur domain intent (task lifecycle vs reflection).
17) Backup restore invalidates core providers, but secondary providers may still depend on stale local caches.
18) Multiple lifecycle side effects use best-effort semantics; non-blocking failures can silently reduce integration fidelity.
19) Tutorial/mission events are partially integrated and may not fully reflect production execution journeys.
20) Supabase health check probes only selected tables/bucket paths, not full operational dependencies.
21) Profile progression and settings persistence are separate and can drift from account expectations.
22) Access gating combines testing and runtime premium paths; behavior may differ by environment flags.

Low:
23) Timeline repository corruption handling returns empty set, potentially masking historical data issues.
24) Local-first repositories have varied corruption policies, producing uneven failure semantics.
25) Integration tests are mostly scaffold-level and may miss deep cross-spoke regressions.
