4) ENTITY INVENTORY AND OWNERSHIP SEMANTICS
TaskEntity:
- Has id/title/kind/description/createdAt/isCompleted/completedAt/scheduledFor/dueDate/goalId/isCanceled/subtasks/recurrenceRule/priority-difficulty-energy.
- No userId.

GoalEntity:
- Has id/title/createdAt/description/targetDate/colorHex.
- No status/completion flag/archived flag/progress counters/userId.

RoutineEntity:
- Has id/name/createdAt/updatedAt/userId?/description/stepTaskIds/status(active-paused-archived).
- No explicit recurrence cadence field; cadence is inferred upstream from creator input.

TimelineEventEntity:
- Has id/type/title/detail/timestamp/status/dueAt/phase/relatedId.
- Works as generalized activity/risk/recommendation stream with event enums.

Assessment:
- Entity coverage is enough for local operation, but ownership and completion semantics are incomplete for long-term normalized domain consistency.

5) TASK MODEL AUDIT
Strengths:
- Rich behavioral state for planner and SI scoring (priority/difficulty/energy/recurrence).
- Explicit completion timestamps and overdue derivation.
- Supports relation to goal via goalId and list of subtask IDs.

Gaps:
- No userId on TaskEntity while cloud auth/user boundaries exist.
- Subtasks modeled as List<String> IDs only; no embedded value object relation contract in entity.
- No explicit task lifecycle enum; lifecycle inferred from isCompleted/isCanceled plus delayed behavior in provider.

Risk:
- Medium: sufficient now, but cross-device and cloud synchronization will need ownership + explicit lifecycle normalization.

6) GOAL MODEL AUDIT
Strengths:
- Clean minimum shape with JSON roundtrip.
- Supports scheduling pressure via targetDate.

Gaps (critical):
- No completion state, archived state, or status enum.
- Downstream use cases for completed/archived goals currently return empty by design.
- No userId.

Observed consequence:
- view_completed_goals_usecase and view_archived_goals_usecase are placeholder-like and cannot model true goal lifecycle.

Risk:
- High: goal analytics and domain correctness are constrained by missing core state.

7) ROUTINE MODEL AUDIT
Strengths:
- Includes status enum and optional userId.
- Has mutable stepTaskIds for linked task structure.

Gaps:
- No recurrence/frequency field in RoutineEntity itself.
- Creator path may tag tasks with kind="routine" and recurrenceRule, but dedicated routines state is separate and weakly coupled.

Risk:
- Medium-high: routine intent exists in creator UX, but domain split between task-like recurrence and routine repository is not normalized.

8) TIMELINE MODEL AUDIT
Strengths:
- Single timeline event abstraction supports task/goal/habit/project/milestone/risk/recommendation.
- Status enum includes planned/active/completed/overdue/atRisk/info.
- Flexible relatedId and dueAt fields support broad read models.

Gaps:
- Timeline mixes events and inferred schedule state (overdue/upcoming/risk) in one envelope.
- No explicit event source taxonomy beyond type and title/detail conventions.
- relatedId is untyped String; no polymorphic reference integrity.

Risk:
- Medium: excellent for UI stream, weaker as durable canonical audit log without normalization rules.

9) CREATOR INTAKE MODEL AUDIT
Current behavior:
- Creator routes data to either goal creation or task creation.
- Modes map to kinds (goal/milestone/plan/routine/note/task).
- Routine mode defaults to daily recurrence when recurrence none is selected.

Gaps:
- CreatorSavedKind returns only task or goal; routine/note/milestone/plan are represented as task kind variants.
- No dedicated NoteEntity path identified.

Risk:
- Medium: intake flexibility is high, but domain specificity is collapsed into task kinds, reducing model clarity.

10) RELATIONSHIP AND CARDINALITY AUDIT
Observed relations:
- Goal 1 -> many Tasks via task.goalId.
- TimelineEvent many -> optional one related domain item via relatedId.
- Routine -> many stepTaskIds.

Missing referential guarantees:
- No typed foreign keys in local stores.
- No enforcement that relatedId points to valid entity type.

Risk:
- Medium.

11) LIFECYCLE AND STATE TRANSITION AUDIT
Task lifecycle:
- create, complete, skip, delay/not_completed, update reflected in task provider with logs/timeline emissions.
- Dedup guard exists for timeline-origin actions.

Goal lifecycle:
- create/update/delete/duplicate exists, but completed/archived semantic state absent.

Routine lifecycle:
- CRUD exists in routines provider with status enum on entity.

Timeline lifecycle:
- record events and emit TimelineLifecycleEvent.

Risk:
- High mainly due to goal lifecycle incompleteness.

12) LOCAL PERSISTENCE AUDIT
TaskRepository:
- Hive-backed per-task payloads; malformed payload detection can fail hard with format exception after counting malformed records.

GoalRepository and RoutineRepository:
- Snapshot corruption guard blocks writes when corrupted.

TimelineRepository:
- SharedPrefs-backed array snapshot.

ProfileRepository:
- SecureStore-backed.

SettingsRepository:
- SharedPrefs-backed with corruption warnings and null fallback.

Assessment:
- Good defensive posture locally; model persistence remains primarily local-first.

16) CONSISTENCY AND NAMING AUDIT
Findings:
- Dual task models (TaskEntity + Task) indicate separation of domain vs read model but increase cognitive load.
- Creator mode kinds include semantic values (milestone/plan/note/routine) without dedicated entities.
- Feature code for goals/timeline exists largely under providers and auth-domain usecases rather than dedicated feature roots.

Impact:
- Medium maintainability tax; not a blocker but raises onboarding and extension complexity.

17) OPTION ANALYSIS: TIMELINE MODEL
Option A: Keep single TimelineEventEntity as canonical store.
- Pros: simple, flexible, already working.
- Cons: weak type integrity, mixed event semantics.

Option B: Split into TimelineEvent (fact) + TimelineProjection (derived risk/upcoming).
- Pros: cleaner event sourcing boundary and analytics consistency.
- Cons: migration and query complexity increase.

Option C: Fully polymorphic timeline with typed references per entity family.
- Pros: strongest integrity.
- Cons: high complexity for current app maturity.

Recommendation:
- Choose Option B (phased). Keep current timeline for UI while introducing explicit derived projection rules.

18) OPTION ANALYSIS: ROUTINE MODEL (A/B/C)
Option A: Keep routines as Task kind + recurrence only.
- Pros: minimum change.
- Cons: routine semantics remain ambiguous.

Option B: Keep RoutineEntity, add explicit recurrence cadence and execution policy fields, maintain links to tasks.
- Pros: strong domain clarity with manageable migration.
- Cons: moderate refactor in creator and routine flows.

Option C: Replace with full Habit domain and deprecate RoutineEntity.
- Pros: potentially clean long-term if habit-first product strategy.
- Cons: largest rewrite and unclear need right now.

Recommendation:
- Choose Option B.

19) OPTION ANALYSIS: COMPLETION MODEL (A/B/C)
Option A: Boolean + timestamp only on each entity.
- Pros: easy.
- Cons: poor auditability and history.

Option B: Add explicit status enums per aggregate (TaskStatus, GoalStatus, RoutineStatus) with optional timestamps.
- Pros: clear lifecycle semantics, easier filtering/reporting.
- Cons: moderate migration.

Option C: Event-sourced completion ledger (CompletionEvent table/model) + projections.
- Pros: best historical fidelity and analytics.
- Cons: highest complexity.

Recommendation:
- Near term: Option B.
- Later if needed: evolve to Option C for deep analytics/audits.
