CHRONOSPARK LOGIC BUILDER AUDIT
Date: 2026-07-30
Mode: Audit only. No code changes.
Scope: Application logic only. This report covers state, workflow, event flow, completion logic, dependency wiring, progression logic, onboarding/tutorial ownership, validation, automation, and production readiness.

============================================================
SECTION 1: EXECUTIVE LOGIC SUMMARY
============================================================
What the app currently does logically:
- ChronoSpark is a local-first planner with a central Creator, a Timeline review layer, task completion side effects, profile progression, and several intelligence surfaces that infer state from tasks, logs, memories, and timeline events.
- Core runtime logic already connects creation -> persistence -> timeline projection -> completion side effects -> momentum/progression -> intelligence summaries.
- The strongest live logic is task creation/completion, goal creation/completion, timeline projection, and progression/momentum derivation.

What the app is intended to do logically:
- Login -> Creator -> create task/routine/goal/note -> choose one time/daily/weekly -> schedule date -> create -> Timeline -> complete/not complete/skip/reschedule -> progression updates -> Smart Planner insights -> Future Vector predictions -> Ascension progression -> SI Console system awareness.

Biggest logic strengths:
- Creator -> task/goal persistence is real and wired.
- Timeline consumes the same core records that Creator writes for tasks and goals.
- Completion actions fan out into logs, timeline events, notifications, profile XP/streak, learning, and momentum.
- The intelligence stack is not purely decorative; it consumes execution signals, trajectory aggregates, memories, and logs.

Biggest logic weaknesses:
- Routine and note are not first-class domain flows; they are routed through task-kind semantics or adjacent memory logic.
- Delete is a domain capability, but it is not part of the main Creator -> Timeline action chain.
- Missed is not a first-class business state; overdue/deferral is stronger than missed.
- Some downstream systems consume aggregates rather than direct domain entities, so dependencies are indirect.

Logic systems that appear unfinished:
- Onboarding usecases are stubbed and do not carry the real flow.
- Some progression and intelligence features infer from task/log aggregates instead of explicit domain records for routines, notes, and missed items.
- Creator supports notes/routines/goals at the UI level, but not all of them have equivalent native storage semantics.

Logic systems that appear duplicated:
- Onboarding exists in multiple layers: OnboardingScreen, onboarding state keys/providers, mission state/progression, and tutorial controller/progress.
- Future/trajectory logic overlaps heavily across trajectorySummaryProvider, futureTimelineProvider, trajectorySimulationProvider, explainableSIProvider, dailyCommandBriefingProvider, and operatorStateProvider.
- Goal progression appears in both goal provider logic and profile-backed progression logic.

Verdict:
- KEEP: core task/goal/timeline/progression/logics that already work.
- REFACTOR: Creator item-type semantics, completion state naming, and intelligence input aggregation.
- MERGE: overlapping onboarding/tutorial/mission flows and overlapping future/trajectory summaries.
- REMOVE: dormant onboarding usecase scaffolding and any logic branches never called from runtime flows.
- UNKNOWN: any route-adjacent behavior that needs runtime verification, especially around dormant onboarding and unused delete surfaces.

SECTION 3: CREATOR LOGIC FLOW
============================================================
User creates task
- UI event: CreatorScreen -> DynamicForm submit.
- Validation: title required, blanks rejected.
- Model creation: TaskEntity built from title, description, type, priority, schedule, recurrence.
- State update: creatorActionsProvider.createEntry -> taskActionsProvider.createTask.
- Provider update: tasksProvider invalidated; goalProgressProvider invalidated; creatorFirstItemCreatedProvider set.
- Persistence: task repository saves the task.
- Timeline update: timelineActionsProvider.connectTask and mirrored task_created log/event side effects.

User creates routine
- UI event: CreatorScreen -> DynamicForm submit with type routine.
- Validation: same title validation; recurrence defaults to daily if unset.
- Model creation: TaskEntity kind routine with daily recurrence fallback.
- State update: creatorActionsProvider -> taskActionsProvider.
- Provider update: tasksProvider, goalProgressProvider, timeline-related invalidations.
- Persistence: task repository saves the routine-like task.
- Timeline update: projected only through task semantics, not a native routine entity.

User creates goal
- UI event: CreatorScreen -> DynamicForm submit with goals workspace mode.
- Validation: title required.
- Model creation: GoalEntity created through goalsProvider, not a task stub.
- State update: goalsProvider notifier add/addDaily/addWeekly.
- Provider update: goalProgressProvider, goal analytics, timeline projections.
- Persistence: goal repository saves the goal.
- Timeline update: timelineProvider reads goals and creates projected goal-related events.

User creates note
- UI event: CreatorScreen -> DynamicForm submit with type note.
- Validation: title required.
- Model creation: TaskEntity kind note is created, not a dedicated MemoryEntity note flow.
- State update: taskActionsProvider createTask.
- Provider update: tasksProvider invalidated, logs/timeline side effects fired.
- Persistence: task repository saves the note-like task entry.
- Timeline update: note is not a native timeline type; it remains indirect unless mirrored elsewhere.

What is fully wired:
- Task creation.
- Goal creation.
- Recurrence defaulting for routines.
- Schedule date capture on create.
- Timeline projection for tasks and goals.

What is partially wired:
- Routine as a native domain type.
- Note as a native domain type.
- Post-save summary/confirmation semantics.
- Better review metadata before persistence.

What is disconnected:
- Separate native note storage from Creator note submissions.
- Separate native routine storage from Creator routine submissions.
- Dedicated delete path inside the main Creator flow.

Creator logic score: 78/100

SECTION 4: TIMELINE LOGIC FLOW
============================================================
Does Timeline read the same records Creator writes?
- Yes for tasks and goals.
- Partially for routines and notes, only if they exist as task-kind entries or mirrored signals.

Can Timeline display task?
- Yes. Task events are first-class timeline items.

Can Timeline display routine?
- Not natively. Routine-like data is only indirectly visible through task-kind semantics.

Can Timeline display goal?
- Yes. Goal events are first-class and are also projected from goalsProvider.

Can Timeline display note?
- Not natively. Notes are not a dedicated timeline event type.

Can Timeline update completed?
- Yes. timeline UI calls completeTask through taskActionsProvider.

Can Timeline update not completed?
- Yes. The timeline UI maps this to delayTask by one day.

Can Timeline update skipped?
- Yes. Skip maps to taskActionsProvider.skipTask.

Can Timeline update rescheduled?
- Yes. Timeline UI maps this to delayTask with a selected duration.

Gaps:
- No native routine or note timeline lane.
- The timeline is stronger for task-state updates than for all creator item types.
- Some timeline items are projected/derived rather than directly stored, which is good for UX but can obscure provenance.

Timeline logic score: 76/100

SECTION 5: COMPLETION LOGIC AUDIT
============================================================
completed
- Data model support: yes. TaskEntity has isCompleted and completedAt; TimelineEventEntity has completed status.
- Provider support: yes. completeTask exists in taskActionsProvider and goal completion exists in goalsProvider.
- UI support: yes. Timeline actions include Complete.
- Storage support: yes. Task repository persists completion; logs/timeline mirror the event.
- Analytics support: yes. task_completed and goal_completed are tracked.

not completed
- Data model support: partial. The business meaning exists, but it is implemented as delayTask by one day rather than a dedicated not-completed state.
- Provider support: yes. Timeline action calls delayTask.
- UI support: yes. Timeline action chip exists.
- Storage support: yes, via updated scheduledFor plus mirrored events.
- Analytics support: indirect. It is counted as a delay rather than a distinct not-completed event.

skipped
- Data model support: yes. Task skip state is stored through logs/timeline, not as a separate task flag.
- Provider support: yes. taskActionsProvider.skipTask exists.
- UI support: yes. Timeline and creator entry lists expose skip.
- Storage support: yes. Logs and mirrored timeline events persist the action.
- Analytics support: yes. task_skipped is tracked.

rescheduled
- Data model support: yes, but through scheduledFor updates rather than a distinct reschedule entity.
- Provider support: yes. delayTask is the runtime implementation.
- UI support: yes. Timeline reschedule chip exists.
- Storage support: yes. TaskEntity.scheduledFor is updated.
- Analytics support: yes. task_delayed is tracked.

missed
- Data model support: no first-class missed event.
- Provider support: no dedicated missed-task action in the audited runtime chain.
- UI support: no explicit missed action.
- Storage support: only indirect, via overdue state or analytic inference.
- Analytics support: no distinct missed event.

overdue
- Data model support: yes. TaskEntity has isOverdue via dueDate; TimelineEventEntity has overdue status.
- Provider support: yes. Timeline projection logic emits overdue states.
- UI support: yes. Timeline filters and badges can show overdue items.
- Storage support: derived from date fields, not a dedicated stored action.
- Analytics support: indirect through momentum, risk, and trajectory signals.

Where the chain breaks:
- Missed is inferred, not stored.
- Not completed is implemented as delay, so business semantics are softer than the label.
- Delete is a repository/domain capability, but not part of the primary completion workflow.

Completion logic score: 78/100

SECTION 12: EVENT FLOW AUDIT
============================================================
Create Item
- Flow: Creator UI -> creatorActionsProvider -> taskActionsProvider or goalsProvider -> repository -> logs/timeline side effects -> analytics -> event bus.
- Stop point: if the relevant repository or side effect fails, the task/goals write can still succeed while supporting telemetry is best-effort.

Update Item
- Flow: taskActionsProvider.updateCreatorEntry or goalsProvider.update -> repository -> log/timeline mirror -> event bus -> invalidations.
- Stop point: update is present for creator entries and goals, but not as a universal Creator action for every domain concept.

Delete Item
- Flow: domain delete usecases exist for tasks/goals/routines/memories, but the main audited Creator/Timeline runtime path does not expose a unified delete action.
- Stop point: delete is a domain capability, not a central workflow event.

Schedule Item
- Flow: Creator captures scheduledFor at creation; Timeline reschedules through delayTask -> task repository update.
- Stop point: schedule is not a separate event stream; it is folded into create or delay semantics.

Complete Item
- Flow: Timeline or creator entry actions -> completeTask / completeGoal -> repository -> timeline/log/notification/progression/learning side effects.
- Stop point: if the task is already completed or missing, completion is rejected.

Skip Item
- Flow: Timeline or creator entry actions -> skipTask -> learning update -> SI state update -> log/timeline mirror -> notification -> event bus.
- Stop point: skip is task-centric and does not map to a separate universal domain event.

Reschedule Item
- Flow: Timeline reschedule chip -> delayTask -> task repository update -> log/timeline mirror -> coach refresh -> event bus.
- Stop point: reschedule is task-centric and implemented as delay.

Login
- Flow: authControllerProvider -> AuthRepository -> session result -> local identity mirror -> authUserProvider/intelligence state.
- Stop point: Google/browser OAuth can temporarily return without a session; state waits for callback/session refresh.

Logout
- Flow: authControllerProvider.signOut -> repository -> local identity clear -> auth state reset.
- Stop point: if sign-out fails, state remains error and user stays in the current session.

Subscription Change
- Flow: paywallActionsProvider.startSubscription/restorePurchases -> subscription/entitlement repositories -> premiumAccessProvider -> appAccessProvider -> UI access changes.
- Stop point: if entitlement or purchase verification fails, premium access does not change.

SECTION 13: VALIDATION & RULES AUDIT
============================================================
Can item save empty?
- No for title. Creator rejects blank title.
- Yes for optional description/details.

Can schedule be invalid?
- Mostly prevented in Creator by date picker bounds.
- Schedule can still be semantically weak because there is no richer validation around item type, recurrence, or target date consistency.

Can duplicate creation occur?
- Yes. There is no strong deduplication rule in the audited create chain; IDs are timestamp-based and user repeat taps are only locally guarded.

Can stale data occur?
- Yes. Local-first providers can diverge temporarily from repository-backed truth, especially when side effects are best-effort.

Can onboarding lock users?
- Partially. Onboarding routes users, but the main logic does not appear to hard-lock them once routing is established.

Can timeline contain orphaned data?
- Yes. Because it is a mix of base events, mirrored events, and projections, orphaned or stale projections are possible if source records are deleted or not synchronized.

Can provider state diverge from persistence?
- Yes. This is a known risk in the current architecture because many providers keep cached state and then invalidate or sync after writes.

Business-rules score: 72/100

SECTION 18: CHRONOSPARK TARGET LOGIC MODEL
============================================================
Ideal chain:
Creator -> Storage -> Timeline -> Completion -> Ascension -> Future Vector -> Smart Planner -> SI Console

What each stage should provide:
- Creator: canonical item type, title, detail, recurrence, schedule, source surface, and user intent.
- Storage: authoritative task/goal/routine/note records, plus lightweight event records for completion and reschedule.
- Timeline: a unified read model of upcoming, active, completed, overdue, and historical items across all item types.
- Completion: explicit states for completed, not completed, skipped, rescheduled, missed, and overdue.
- Ascension: XP, level, streak, routine consistency, goal achievement, and completion quality.
- Future Vector: planned load, completion rate, goal progress, schedule health, missed-item pressure, and recovery risk.
- Smart Planner: direct access to tasks, goals, routines, notes, completion history, schedule health, and user context.
- SI Console: a transparent read layer over task/goal/routine/note/timeline/completion/profile/subscription/settings state.

Desired data flow rule:
- Each stage should enrich, not reinterpret, the previous stage. Aggregates are useful, but native entities should remain visible underneath.
