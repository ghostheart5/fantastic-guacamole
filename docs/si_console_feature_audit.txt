FINDINGS (ordered by severity)

[Medium] The visible command chip registry is stale and incomplete relative to the supported local command surface
- Location: si_console_screen.dart + si_console_commands.dart
- Evidence:
  - The input bar renders chips from SIConsoleCommands.values.
  - SIConsoleCommands.values currently contains only /help, /status, /tasks, /goals, /plan, /timeline, and /trajectory.
  - The screen actually handles many more local commands, including /milestones, /values, /soulmap, /simulate, /success, /risk, /lessons, /patterns, /future, /identity, /paths, /evolution, /timelinefuture, /decision, /twin, /fusion, /replan, and /momentum.
- Impact:
  - The visible command surface under-represents the real feature surface.
  - Users are steered toward a small subset of commands while several supported console paths remain undiscoverable from the chip UI.
  - The registry can mislead future maintainers into believing the console only supports a narrow command set.
- Recommendation:
  - Keep the runtime command behavior as-is, but update the chip registry or derive it from the same command map so the visible shortcuts stay aligned with the actual handler surface.

[Low] Provider errors are only shown when the message list is empty, so later SI Console failures can be hidden by prior chat content
- Location: si_console_screen.dart
- Evidence:
  - The body shows ErrorView only when consoleError != null && _messages.isEmpty.
  - Once the greeting or any prior exchange exists, the screen continues to render the message list even if siConsoleScreenModelProvider later exposes an error.
- Impact:
  - A refreshed or late-failing SI console model can fail silently from the user’s perspective.
  - Existing messages keep the screen functional, but the underlying model error is no longer visible.
  - This makes diagnosis harder when integration snapshot or engine snapshot refreshes fail after the console has already opened.
- Recommendation:
  - Surface a compact inline error banner or retry hint even when messages already exist, or otherwise preserve an error indicator outside the empty-state branch.

FEATURE / WIRING MAP

1) Local command surface
- Source:
  - _handleLocalCommand() in si_console_screen.dart
  - SIConsoleCommands.values in si_console_commands.dart
- Behavior:
  - Handles signal channels for tasks, goals, milestones, values, soulmap, plan, timeline, trajectory, momentum, simulation, future, identity drift, paths, evolution, future roadmap, decision, twin, fusion, replanning, success, risk, and lessons/patterns.

2) Console summary model
- Source:
  - siConsoleScreenModelProvider in si_pipeline_provider.dart
- Behavior:
  - Builds engineSnapshot and integrationSnapshot from aggregation, SI engine state, and integration snapshot data.
  - The screen uses it to drive header status and the initial loading/error state.

3) Execution / trajectory flow
- Source:
  - executionSignalsProvider
  - trajectorySummaryProvider
  - momentumEngineProvider
  - trajectorySimulationProvider
  - futureTimelineProvider
  - identityDriftProvider
  - futureDecisionEngineProvider
- Behavior:
  - Provides the trajectory and forecast content used by /trajectory, /simulate, /future, /identity, /decision, /momentum, and /timelinefuture.

4) Prompt copy / command hints
- Source:
  - SIConsolePromptCopy
- Behavior:
  - Supplies help text and reusable prompt wording for the console response strings.

INPUTS / OUTPUTS SUMMARY

Inputs consumed by SI Console:
- SI aggregation snapshot
- profile, momentum, trajectory, drift, future decision, future timeline, simulation, core values, soul map, execution signals, and model integration snapshot data
- user text input and local command shortcuts

Outputs produced by SI Console:
- Local command summaries for multiple SI surfaces
- Assistant chat messages
- Voice summary and accessibility guidance
- Navigation back to the app shell

OVERALL ASSESSMENT
- The SI Console screen is functionally rich and the command handlers are active.
- The main quality risk is discoverability drift: the command chips expose only a small subset of the actual supported commands.
- The second risk is error visibility: once the console has messages, provider failures can be hidden behind the existing conversation UI.
