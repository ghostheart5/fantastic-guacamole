CHRONOSPARK APP DEPLOYMENT / ALM BUILDER AUDIT

Audit mode: read-only
Scope reviewed: android/, ios/, .github/, .gitignore, pubspec.yaml, analysis_options.yaml, README.md, and build/release scripts

============================================================
SECTION 1
EXECUTIVE ALM SUMMARY
============================================================

Deployment maturity:
- Moderate.
- Android release build automation exists with strong signing and production-define gates in .github/workflows/android-release.yml and scripts/build_android_aab_prod_guarded.ps1.
- Web deployment automation exists for GitHub Pages in .github/workflows/main.yml.
- Linux tester release workflow exists in .github/workflows/linux-release.yml.
- iOS release automation is not present in GitHub workflows.

Release maturity:
- Moderate.
- Versioning is explicit in pubspec.yaml and mirrored into android/gradle.properties by guarded scripts.
- Tagged release trigger exists for Android (v*.*.* tags).
- Artifact generation and GitHub Release creation are automated.
- Google Play publish step is not automated.

Rollback readiness:
- Low to moderate.
- App artifact rollback can be done manually by selecting prior builds/releases.
- No automated mobile rollout rollback orchestration is present.
- Data rollback strategy is not represented in deployment scripts.

Production readiness:
- Moderate.
- Strengths: release signing checks, upload key fingerprint checks, required production env validation, secret guard script.
- Gaps: no automated Play publish/rollback runbook in CI, no explicit staging pipeline, no iOS production pipeline.

SECTION 4
SUPABASE ENVIRONMENT AUDIT
============================================================

Dev vs prod separation:
- Separation is primarily via runtime defines (CHRONOSPARK_APP_FLAVOR and CHRONOSPARK_SUPABASE_* defines in lib/config/env.dart and release scripts).
- Prod scripts require explicit Supabase URL and anon key.

Environment risks:
- Same variable names are reused across environments, increasing risk of pointing tester builds at production if operator discipline fails.
- No dedicated staging-specific Supabase variable set was found.

URL management:
- Managed through dart-defines and optional .env fallback.
- Account delete and monetization verify endpoints can derive from Supabase URL when not explicitly set.

Key management:
- Anon key is supplied via secrets/env.
- Secret guard blocks tracked .env and key files.
- Overall pattern is acceptable for client-side anon key use, but environment segregation discipline is critical.

SECTION 10
RELEASE RISK REGISTER
============================================================

Top 25 deployment risks:

1. No automated Google Play publish pipeline (manual store step risk).
2. No automated Play staged rollout management.
3. No automated Play rollback path.
4. No iOS App Store release pipeline.
5. Staging flavor exists but no dedicated staging deployment lane.
6. Single Firebase project mapping visible across environments.
7. Supabase environment separation relies on operator-set variables only.
8. Tester and prod script variable names are very similar; mis-targeting risk.
9. Android release workflow does not run full analyze/test gate before bundle.
10. Release scripts mutate pubspec.yaml and android/gradle.properties directly.
11. Potential version drift if scripted changes are not committed/tagged consistently.
12. No automated release notes/changelog generation.
13. PR policy allows only one maintainer actor, creating single-point release bottleneck risk.
14. Linux release workflow produces draft prerelease only; no promotion governance step.
15. Web deployment on main push can publish without explicit release approval gate.
16. No explicit environment protection rules are visible in workflows for release jobs.
17. No explicit mobile canary rollout controls in CI.
18. No explicit mobile post-deploy synthetic monitoring pipeline.
19. Data rollback plan is not codified in deployment scripts.
20. Config rollback playbook is not codified beyond manual secret edits.
21. Secret guard focuses on tracked files; runtime secret misuse still possible.
22. Android release depends on accurate keystore alias resolution and keytool availability.
23. iOS signing/team automation is not visible in CI, increasing manual release fragility.
24. Cross-platform release orchestration is fragmented (Android, Linux, Web separated).
25. Limited formal ALM evidence for release approval, audit trail, and promotion gates.

SECTION 12
SAFE RELEASE ROADMAP
============================================================

Target progression: Closed Testing -> Production

Phase 1: Closed Testing Baseline
- Freeze tester build recipe and naming convention.
- Require strict_gate + release_guard before tester bundle generation.
- Produce signed tester AAB with QA flavor and explicit non-prod flags.

Phase 2: Environment Segmentation
- Define explicit variable sets for dev/test/staging/prod in CI documentation.
- Add staging deployment lane (build + smoke + deploy target) before prod.

Phase 3: Promotion Controls
- Introduce release candidate workflow requiring explicit manual approval before prod artifact creation.
- Add artifact provenance checks (hash + metadata + version map).

Phase 4: Store Automation Foundations
- Add Play upload automation in dry-run/validation mode first.
- Add track promotion workflow (internal -> closed -> production) with approvals.

Phase 5: Rollback Readiness
- Codify app rollback SOP for Play tracks.
- Codify config rollback SOP (secrets/env rollback matrix).
- Add release runbook checklist artifact per release.

Phase 6: Production Hardening
- Gate Android release workflow with required analyze/test subset.
- Add post-release synthetic smoke checks and alerting hooks.

Phase 7: iOS ALM Parity
- Add iOS build/sign/archive workflow with equivalent environment and readiness checks.
