============================================================
SECTION 1
EXECUTIVE SECURITY SUMMARY
============================================================

Current posture summary:
- Overall security maturity: Medium-High.
- Strong controls exist across transport security, auth gating, secure storage usage, JWT-verified edge functions, and release guards.
- Main residual risk is configuration drift and credential hygiene, not a core absence of controls.

Top strengths:
- HTTPS enforcement for critical endpoints.
- Deep-link trust filtering and app-link constraints.
- RLS-enabled Supabase tables and ownership policies.
- Secret guard and release guard scripts in repo.
- Redaction patterns in runtime logging.

Top risks:
- Presence of local .env and multiple .bak files under lib/ increase accidental exposure surface.
- Firebase project keys and identifiers are present in generated client config (common, but still reconnaissance-friendly if combined with weak backend policy).
- Mock/auth fallback paths must remain strictly non-production.

SECTION 2
AUTHENTICATION AUDIT
============================================================

Findings:
- Auth provider uses Supabase via AuthService with email/password, OAuth Google, OTP, password reset, and session refresh logic.
- Exponential backoff exists for repeated sign-in failures.
- Account deletion requires re-authentication and bearer-based secure endpoint call.
- UnavailableAuthService fails closed when backend is not configured.

Risk notes:
- Mock and always-authenticated service implementations exist; these are acceptable for non-production but must never be reachable in production flavor.

Rating:
- 8/10

SECTION 25
SAFE REMOVE-LATER STRATEGY
============================================================

Safety policy:
- Do not delete backup-like files from lib/ in ad-hoc edits.
- Quarantine candidates first; remove only via reviewed cleanup PR with:
	- ownership acknowledgement,
	- no-runtime-reference proof,
	- post-removal test pass.

Removal phases:
- Phase R1 (audit): keep inventory list up to date and confirm files are not imported/referenced.
- Phase R2 (quarantine): move candidates to a non-runtime archive folder outside lib/ with explicit changelog entry.
- Phase R3 (remove): delete only after one full release cycle without regressions.

Rollback:
- If regression appears after R2 or R3, restore from VCS immediately and re-open the cleanup item as blocked.
