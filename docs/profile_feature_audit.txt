FINDINGS (ordered by severity)

[High] Connected Accounts state is hard-coded and can be stale/inaccurate versus actual identity state
- Location: account_connection_provider.dart
- Evidence:
  - Provider returns a const AccountConnectionState with fixed entries.
  - EMAIL is always marked connected and GOOGLE always disconnected, independent of identity/session data.
- Impact:
  - UI can present false account connection truth to users.
  - Reduces trust in profile/account center and can mislead support/debug workflows.
- Recommendation:
  - Derive connection statuses from real identity/auth session sources instead of static constants.

[Medium] Identity action failures are not surfaced in Profile UI
- Location: profile_screen.dart + identity_account_actions_provider.dart
- Evidence:
  - UI reads identityActionState.isLoading only.
  - No explicit handling for AsyncError in _IdentityAccountActionsCard.
- Impact:
  - Failed initialize/restore/sign-out can appear silent.
  - User receives no clear remediation guidance when local identity operations fail.
- Recommendation:
  - Render a compact error status/retry hint when action provider is in error state.

[Medium] Profile view state abstraction exposes loading/error but never practically used
- Location: profile_view_state.dart + profile_service.dart + profile_provider.dart
- Evidence:
  - ProfileViewState includes loading/error.
  - fromControllerState() always returns loading=false, error=null.
- Impact:
  - Surface contract suggests async/error states that are not wired, increasing maintenance ambiguity.
  - Future contributors may assume reliability/error handling that does not exist.
- Recommendation:
  - Either wire real loading/error signals or simplify the view model contract.

[Medium] Profile feature uses mixed architecture paths (modern identity providers + legacy profile controller model)
- Location: profile_screen.dart composition
- Evidence:
  - Screen simultaneously pulls profileViewStateProvider (legacy profile state mapping), identityAccountStatusProvider, accountSecurityProvider, accountConnectionProvider, and identityAccountActionsProvider.
- Impact:
  - Increases cognitive load and coupling in one screen.
  - Raises risk of inconsistent state transitions across profile surfaces.
- Recommendation:
  - Introduce a single ProfileScreenViewModel provider that composes these sources consistently.

[Low] Profile Controller default name and onboarding default name differ
- Location: profile_controller.dart and onboarding flows
- Evidence:
  - ProfileState default name is "Operative" while onboarding fallback often uses "Operator".
- Impact:
  - Minor naming inconsistency across user journey.
- Recommendation:
  - Standardize default naming policy across profile initialization surfaces.

[Low] Account hub billing route visibility is unconditional in UI
- Location: profile_screen.dart
- Evidence:
  - Billing center button always shown and pushes RoutePaths.subscriptionManagement.
- Impact:
  - Potential UX mismatch if billing access/state differs by auth mode.
- Recommendation:
  - If product expects auth/subscription gating, align button visibility/label with runtime entitlement state.

PROFILE FEATURE LOGIC/WIRING MAP

1) Core Profile Data Flow
- Source:
  - profileProvider (NotifierProvider<ProfileController, ProfileState>)
- Mapping:
  - profileFeatureServiceProvider -> ProfileService.fromControllerState()
  - profileViewStateProvider exposes ProfileViewState(profile, loading=false)
- UI usage:
  - ProfileScreen reads profileViewStateProvider as base metrics/header data

2) Identity Account Flow
- Source:
  - identityAccountProvider (ChronoSparkIdentity?)
- Derived display:
  - identityAccountStatusProvider maps identity -> display labels (name/tier/sync/email)
- Actions:
  - identityAccountActionsProvider (AsyncNotifier<void>) for initialize/restore/sign-out
  - Uses LocalIdentityRepository (SharedPreferences persistence)
- UI usage:
  - _IdentityAccountCard + _IdentityAccountActionsCard

3) Account Security Flow
- Source:
  - accountSecurityProvider derives level flags from identityAccountProvider
- Derived outputs:
  - level, summary, recommendation, chips (EMAIL/SESSION/DEVICE/RESET)
- UI usage:
  - _AccountSecurityCard

4) Connected Accounts Flow
- Source:
  - accountConnectionProvider (currently static constants)
- UI usage:
  - _ConnectedAccountsCard filters to EMAIL/GOOGLE and displays connection status chips

5) Momentum + Progress Signals
- Source:
  - momentumEngineProvider (trend/forecast/score/energy/pressure/recovery)
  - profile metrics from profile view state (level/xp/streak)
- UI usage:
  - Momentum trend card + metric tiles + operator status card

INPUTS / OUTPUTS SUMMARY

Inputs consumed by Profile screen:
- ProfileState fields (name, level, xp, streak, soundEnabled)
- Identity account status data (derived from ChronoSparkIdentity)
- Security state derived from identity
- Connection state (currently static provider)
- Momentum engine summary state

Outputs produced by Profile feature:
- Navigation outputs:
  - back to nexus
  - open settings
  - push billing center route
- Identity mutation outputs:
  - initialize local identity
  - restore local identity
  - sign out local identity
- Persistence outputs:
  - local identity saved/loaded/cleared via SharedPreferences-backed repository

USECASES / SERVICE SURFACES INVOLVED
- ProfileController persistence:
  - SecureStore + legacy hive migration path for profile state
- Progress side effects:
  - profile XP/streak updates trigger SI decision refresh and optional notification scheduling
- Identity persistence:
  - LocalIdentityRepository (shared preferences key chronospark.identity)

OVERALL ASSESSMENT
- The Profile screen is functionally rich and visually coherent, with strong identity/security presentation.
- The highest-risk issue is static connected-account data that can diverge from real auth/identity state.
- Secondary concerns are error-surface gaps and mixed-state composition complexity.

PRIORITY NEXT FIXES (recommended order)
1) Replace static accountConnectionProvider data with runtime-derived statuses.
2) Surface async identity action errors in _IdentityAccountActionsCard.
3) Decide whether ProfileViewState loading/error should be real or removed from contract.
