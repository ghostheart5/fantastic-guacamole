1. Every notification permission source
- notificationPermissionListenableProvider in lib/state/providers/settings_ui_provider.dart
  - Wraps reflectionReminderServiceProvider.permissionListenable.
- reflectionReminderServiceProvider.permissionListenable in lib/state/services/reflection_reminder_service.dart
  - Delegates to NotificationScheduler.permissionGrantedListenable.
- NotificationScheduler.permissionGrantedListenable in lib/system/notifications/notification_scheduler.dart
  - Global ValueNotifier<bool?> used as the granted/denied boolean source.
- notificationPermissionStateListenableProvider in lib/state/providers/settings_ui_provider.dart
  - Wraps the static NotificationPermissionState ValueNotifier owned by SettingsUiActions.
- SettingsUiActions._notificationPermissionStateListenable in lib/state/providers/settings_ui_provider.dart
  - Global ValueNotifier<NotificationPermissionState> used as the detailed permission source.

2. Which source controls granted boolean
- The granted boolean comes from notificationPermissionListenableProvider.
- That provider reads reflectionReminderServiceProvider.permissionListenable, which reads NotificationScheduler.permissionGrantedListenable.
- In Settings UI, this value is passed as permissionGranted to NotificationPermissionPrompt and also read for the notification status tile.

3. Which source controls detailed permission state
- The detailed permission state comes from notificationPermissionStateListenableProvider.
- That provider reads SettingsUiActions.notificationPermissionStateListenable.
- The detailed state is based on NotificationPermissionState values: granted, denied, permanentlyDenied, unknown.

4. Which source updates after permission request
- The granted boolean source updates when NotificationScheduler.requestPermissions() / init(requestPermissions: true) runs.
- That path sets NotificationScheduler.permissionGrantedListenable.value to the result.
- The detailed source updates when SettingsUiActions.requestNotificationPermissionDetailed() is used, because it calls ReflectionReminderService.requestNotificationPermissionDetailed(), which requests permission and then calls getNotificationPermissionState().
- In SettingsScreen, the notification prompt uses requestNotificationPermissionDetailed(), so both the boolean source and detailed source are refreshed through the underlying scheduler request plus the follow-up state query.

5. Which source updates after returning from system settings
- The current code does not show a dedicated lifecycle refresh on app resume for notification permission.
- openSystemAppSettings() only launches device settings; it does not itself refresh either notification source.
- After the user returns from system settings, the boolean source is only updated if something else later reinitializes or requests permissions through NotificationScheduler.
- The detailed source is also not automatically refreshed on return; it only changes when requestNotificationPermissionDetailed() or refreshNotificationPermissionState() is called.
- Net result: returning from system settings does not reliably refresh either source by itself.

6. Whether the two sources can drift
- Yes.
- The boolean source and detailed source can drift because they are updated by different mechanisms and are not tied to a single refresh pathway.
- The boolean source can change via NotificationScheduler.init/requestPermissions and platform initialization behavior.
- The detailed source can change via a separate permission status query in ReflectionReminderService.getNotificationPermissionState().
- If the user changes notification permission in system settings and the app returns without an explicit refresh, the UI can keep stale values until another permission-related action occurs.
- The two sources are related, but they are not guaranteed to stay synchronized in all lifecycle paths.

7. Recommended single source of truth
- Recommended source of truth: NotificationScheduler.permissionGrantedListenable, backed by a single refresh method that also computes the detailed NotificationPermissionState when needed.
- Why this is the best anchor:
  - It already powers the granted boolean.
  - It is the live scheduler-level permission signal used by app routing and reminder behavior.
  - The detailed state can be derived from a single refresh query instead of being maintained independently as a separate global notifier.
- Practical shape:
  - Keep one live permission signal.
  - Derive the detailed UI state from a single service call or a single cached state object owned by the same service/provider boundary.

8. Safe phased fix
- Phase 1: Add a single explicit refresh entry point for notification permission state at the service boundary.
  - On app resume, and after returning from system settings, call that refresh path once.
  - Keep current UI behavior intact while ensuring both values are refreshed together.
- Phase 2: Move the detailed state onto the same ownership boundary as the boolean state.
  - Replace the separate static ValueNotifier<NotificationPermissionState> with a derived state tied to the same source.
  - Keep the UI contract the same so the screen only receives one coherent permission model.
- Phase 3: Simplify the Settings UI contract.
  - Pass a single composite permission model into NotificationPermissionPrompt rather than two separate listenables.
  - Remove the split only after the screen no longer depends on two independent sources.

OVERALL ASSESSMENT
- The Settings notification permission flow is using two separate listenable sources that can drift.
- The granted boolean is sourced from the scheduler listenable, while the detailed state is sourced from a second static notifier in SettingsUiActions.
- Permission request flows refresh both values indirectly, but returning from system settings does not currently guarantee a refresh.
- The safest long-term design is a single permission state owner with one refresh path and one UI-facing composite model.
