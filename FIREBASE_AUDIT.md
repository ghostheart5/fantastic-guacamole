## Summary

Firebase integration is **correctly wired** — notably the error-routing, which is the part most projects get wrong. Both `FlutterError.onError` and `PlatformDispatcher.instance.onError` route to Crashlytics, the FCM background handler is a top-level function with `@pragma('vm:entry-point')` that re-initializes Firebase in its own isolate, and the Crashlytics Gradle plugin is on the classpath so native crashes and NDK symbols upload.

The problems are configuration hygiene, two unused SDKs, and one silent-degradation path in CI.

## FB-01 · MEDIUM · Release silently ships without Firebase if a CI secret is unset

**Files:** `android/app/build.gradle.kts:11-22` · `.github/workflows/android-release.yml:78-81`

```kotlin
val googleServicesJsonFile = project.file("google-services.json")
val hasGoogleServicesJson = googleServicesJsonFile.exists()

if (hasGoogleServicesJson) {
    apply(plugin = "com.google.gms.google-services")
    apply(plugin = "com.google.firebase.crashlytics")
} else {
    logger.lifecycle("google-services.json was not found … Skipping Firebase Gradle plugins for this build.")
}
```

The CI step is named **"Configure optional Firebase Android file"** and sources the file from `secrets.ANDROID_GOOGLE_SERVICES_JSON_BASE64` / `ANDROID_GOOGLE_SERVICES_JSON`.

**Impact:** The conditional is defensible for local development — it lets contributors build without Firebase credentials. In the **release** path it is a silent-failure mode. If either secret is unset, misnamed, or malformed, the build still succeeds and produces a signed, shippable AAB with:

- no Crashlytics Gradle plugin → **no native crash reporting, no NDK symbol upload, no deobfuscated stack traces**
- no `google-services` plugin → no `google-services.xml` resource → runtime Firebase init fails
- Analytics, Remote Config, and FCM all inert

The only signal is a `logger.lifecycle` line buried in Gradle output. Nothing fails.

**Production risk:** A release that appears healthy while being completely blind to crashes. Because minification is enabled (`isMinifyEnabled = true`), any crash that *is* reported by other means is obfuscated and unreadable without the mapping upload the missing plugin would have performed.

**Fix:** Make the release path strict:

```kotlin
val isReleaseBuild = gradle.startParameter.taskNames.any { it.contains("Release", ignoreCase = true) }
if (!hasGoogleServicesJson && isReleaseBuild) {
    error("google-services.json is required for release builds.")
}
```

And assert in CI before building:

```yaml
- name: Assert Firebase config present
  run: test -s android/app/google-services.json || { echo "::error::google-services.json missing"; exit 1; }
```

## FB-02 · MEDIUM · No FCM default notification channel or icon declared

**File:** `android/app/src/main/AndroidManifest.xml` — searched, absent

The manifest declares no:

```xml
<meta-data android:name="com.google.firebase.messaging.default_notification_channel_id" android:value="..." />
<meta-data android:name="com.google.firebase.messaging.default_notification_icon"       android:resource="..." />
<meta-data android:name="com.google.firebase.messaging.default_notification_color"      android:resource="..." />
```

**Impact:** For **notification messages** delivered while the app is backgrounded, the system — not the app — builds the notification. Without a declared channel ID, Android 8+ places it on a fallback channel named "Miscellaneous", outside whatever channels the app created via `flutter_local_notifications`. Users who tune notification settings per-channel find their preferences ignored. Without a declared icon, Android falls back to `@mipmap/ic_launcher`, which on API 21+ renders as a **solid white or grey square** because notification icons must be white-on-transparent silhouettes.

**Production risk:** Visibly broken push notifications, and per-channel user preferences that silently do not apply. Only affects FCM `notification` payloads; `data`-only payloads handled in Dart are unaffected.

**Fix:** Add a dedicated white-silhouette drawable (`res/drawable/ic_notification.xml`), declare all three meta-data entries, and use a channel ID that matches one created by `flutter_local_notifications` so foreground and background notifications share settings.

## FB-03 · MEDIUM · Two authentication systems coexist

**Dependencies:** `firebase_auth: ^6.5.4` and `supabase_flutter: ^2.16.0` — both used.

Two independent identity providers, each with its own user ID space, session lifecycle, and token format.

**Impact:** The authoritative identity must be unambiguous, because Supabase RLS keys entirely off `auth.uid()` — a Supabase-issued UUID. If any code path treats a Firebase UID as the identity, or if a user can hold a valid Firebase session without a corresponding Supabase session, then:

- Supabase reads/writes execute unauthenticated and RLS denies them (best case), or
- data is written under a mismatched owner and becomes unreachable (worse), or
- the app believes the user is signed in while the backend does not (worst — silent data loss).

Sign-out is the sharpest edge: signing out of one provider while the other retains a session leaves a half-authenticated state. `SUP-05` compounds this — a user can exist in `auth.users` with no `profiles` row.

**Fix:** Document which provider is authoritative. The pragmatic split for this architecture is Supabase as the identity of record (because RLS depends on it), with Firebase Auth used only if a Firebase-specific feature requires it — and if nothing does, remove `firebase_auth` entirely. Ensure sign-out clears **both** providers plus all local stores. Add an integration test asserting that after sign-out, no `Supabase.instance.client.auth.currentSession` and no `FirebaseAuth.instance.currentUser` remain.

## FB-04 · MEDIUM · Firestore and Storage SDKs declared but never imported

**File:** `pubspec.yaml:82-83`

```yaml
cloud_firestore: ^6.6.0     # 0 import sites across all Dart source
firebase_storage: ^13.4.3   # 0 import sites
```

Both federate to large native SDKs. `google-services.json` provisions `chronospark-app.firebasestorage.app`, so the bucket exists even though nothing writes to it.

**Impact:** APK size and method count for zero functionality, a wider minification surface, and extra Firebase component registration at startup. It also creates a false impression that a Firestore data model exists — which in turn makes the missing rules files (FB-06) look like a critical gap when they are not.

**Fix:** Remove both. See `DEPENDENCY_AUDIT.md` DEP-02.

## FB-05 · LOW · Stale `com.example.chronospark` client registration

**File:** `android/app/google-services.json`

```
"package_name": "com.example.chronospark"          ← stale
"package_name": "com.ghostheart5.chronospark"      ← current
```

A leftover from before the package rename. The Gradle plugin matches on `applicationId`, so the correct entry is used and the build is unaffected.

**Impact:** Cosmetic, with two small consequences: the Firebase console shows a phantom app that will never report data, and any SHA-1/SHA-256 certificate fingerprints registered against the stale entry are inert — a plausible source of confusion when debugging Google Sign-In, which validates against fingerprints on the *matching* client.

This mirrors the orphaned `android/app/src/main/kotlin/com/example/fantastic_guacamole/MainActivity.kt` noted in `GOOGLE_PLAY_AUDIT.md` — the same incomplete rename.

**Fix:** Delete the `com.example.chronospark` app from the Firebase console, re-download `google-services.json`, and commit the single-client version.

## FB-06 · LOW · No security rules files in the repository

Searched the whole repo: no `firestore.rules`, no `storage.rules`, no `firestore.indexes.json`.

**Impact:** Normally this would be significant — rules unmanaged in version control means the security posture of the data layer is invisible to review and cannot be diffed, tested, or rolled back. Here it is **LOW because neither product is used** (FB-04). The Storage bucket is provisioned but nothing reads or writes it.

**This becomes HIGH the moment either SDK is actually used.** If Firestore or Firebase Storage is adopted, the rules must land in the same commit, with `firebase.json` wired to deploy them and the emulator suite used to test them.

**Fix:** Remove the unused SDKs (preferred), or add rules files now and reference them from `firebase.json`.

## FB-07 · LOW · `firebase.json` hosting configuration

**File:** `firebase.json` (1,861 bytes)

`.firebaserc` targets `chronospark-app`, but the web app is deployed to **GitHub Pages** by `.github/workflows/main.yml` (`actions/deploy-pages@v4`), not Firebase Hosting.

**Impact:** Two hosting configurations for one web app. If Firebase Hosting was ever deployed, a stale copy of the app may still be live at `chronospark-app.web.app` — serving outdated code against the same Firebase project, and potentially an origin not covered by the edge functions' `ALLOWED_ORIGINS` (`https://chronospark.app`, `https://www.chronospark.app`).

**Fix:** Confirm which host is authoritative. If GitHub Pages, run `firebase hosting:disable` and remove the `hosting` block. If Firebase Hosting, retire the Pages workflow. Either way, align `ALLOWED_ORIGINS` in both edge functions with the real origin.

## FB-08 · INFO · Collection defaults and consent

**Files:** `.env` · `lib/system/firebase/firebase_bootstrap.dart:24`

```
CHRONOSPARK_ENABLE_ANALYTICS       = false
CHRONOSPARK_ENABLE_CRASH_REPORTING = false
```

```dart
await FirebaseCrashlytics.instance.setCrashlyticsCollectionEnabled(...)
```

Both default to **off**, and Crashlytics collection is explicitly gated rather than left at the SDK default — good practice, and the privacy-respecting default.

Two consequences to confirm:

1. **These are the values a local release build gets.** CI overrides them via `--dart-define` (`android-release.yml:122-125`), but a developer running `flutter build appbundle --release` produces an app with no crash reporting at all. See `SECURITY_AUDIT.md` for the full build-path divergence analysis.
2. **Whether the gate is user consent or a build flag is unverified.** For GDPR/UK-GDPR, analytics collection needs a lawful basis; crash reporting is usually defensible as legitimate interest, but analytics generally requires consent. Confirm the flag is wired to a user-facing choice, not only to build configuration.

`AndroidManifest.xml:4-12` removes `AD_ID`, `ACCESS_ADSERVICES_AD_ID`, and `ACCESS_ADSERVICES_ATTRIBUTION` via `tools:node="remove"` — this materially simplifies the Play Data Safety declaration and is the right call.

## B. What is correctly implemented

Recording explicitly so it is not disturbed.

### Crash reporting — both error channels routed

**File:** `lib/app/startup/app_bootstrap.dart:72-110`

```dart
FlutterError.onError = (errorDetails) {
  ...
  FirebaseCrashlytics.instance.recordFlutterFatalError(errorDetails);   // line 93
};

PlatformDispatcher.instance.onError = (Object error, StackTrace stack) {
  ...
  FirebaseCrashlytics.instance.recordError(error, stack, fatal: true);  // line 110
};
```

Both handlers are required for full coverage — `FlutterError.onError` catches framework errors, `PlatformDispatcher.instance.onError` catches errors escaping the Dart isolate outside the framework. Projects commonly wire only the first and lose async errors. This one wires both.

### FCM background handler — correct isolate setup

**File:** `lib/system/firebase/firebase_messaging_bootstrap.dart:10-35`

```dart
@pragma('vm:entry-point')
... async {
  await Firebase.initializeApp(   // line 13 — required: background handler runs in a separate isolate
  ...
}
FirebaseMessaging.onBackgroundMessage(firebaseMessagingBackgroundHandler);   // line 35
```

The `@pragma('vm:entry-point')` annotation prevents tree-shaking in release builds, and `Firebase.initializeApp` inside the handler is required because the background isolate does not inherit the main isolate's Firebase instance. Both are commonly omitted; both are present.

### Crashlytics Gradle plugin on the classpath

**Files:** `android/settings.gradle.kts:22-24` · `android/app/build.gradle.kts:16-17`

```kotlin
id("com.google.gms.google-services") version("4.4.2") apply false
id("com.google.firebase.crashlytics") version("3.0.7") apply false
```

Without the Crashlytics Gradle plugin, mapping files never upload and every release stack trace is obfuscated. It is present and current — subject to the FB-01 conditional.
