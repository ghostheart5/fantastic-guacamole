ChronoSpark — Voice / Audio / Speech Full Audit Report

Overall assessment: RISKY — functional but with a confirmed navigation bug, a critical UX label collision, and several latent state management hazards.

Most likely cause of the speak/mic → Nexus bug:
The _MicButton in lib/features/home/ui/smart_coach_screen.dart is a combined STT-input + voice-command-router widget. When the user stops speaking and the recognized text contains phrases such as "briefing", the parser resolves to VoiceCommandIntent.showBriefing, which directly calls flow.toNexus(). This is intentional routing code — but it is a surprise to users who did not say a navigation command. Additionally, if the STT engine mishears any spoken word as one of these patterns, navigation fires silently.

STT and TTS separation:
Partially separated at the service level — VoiceService (TTS only) and VoiceController (STT only) are distinct — but in the UI they share the same label "SPEAK" on two different buttons in the same widget row, making them indistinguishable to users.

Large/audio assets:
Clean for current size, but noise.png (1.36 MB), app_icon.png (1.22 MB), several unused background JPGs, and uncompressed WAV audio files are worth addressing before release.

1. Executive Summary
- Is the voice/audio system safe, risky, or broken?
  Risky.
- Most likely cause of the speak/mic to Nexus bug
  The _MicButton routes recognized voice commands to navigation targets, and the showBriefing intent routes directly to Nexus.
- Whether STT and TTS are properly separated
  Partially. They are implemented as separate services, but the UI labels and semantics are conflated.
- Whether large/audio assets are clean
  Mostly acceptable, but there are a few large unused files and uncompressed audio assets worth reviewing.

2. Critical Bugs
- BUG-1 — _MicButton routes to Nexus on voice command match (CONFIRMED)
  File: lib/features/home/ui/smart_coach_screen.dart
  Trigger: User taps mic, speaks anything containing the phrase "briefing", then taps mic again to stop.
  Exact code path:
  _MicButton.onTap -> stopListening() -> _latestVoiceText() -> _routeVoiceCommand()
  -> VoiceCommandParser.parse() -> VoiceCommandIntent.showBriefing -> flow.toNexus()
  Why it fires unexpectedly:
  The parser resolves "briefing" to a navigation intent and routes directly to Nexus.
  Severity: Critical.

- BUG-2 — Stale lastResponse from previous STT session can trigger a command
  File: lib/state/controllers/voice_controller.dart
  Problem: After stopListening, the controller may reuse previous transcript state if a new session fails or is interrupted.
  Severity: High.

- BUG-3 — Two buttons both labeled "SPEAK" in the same row
  File: lib/features/home/ui/smart_coach_screen.dart
  Rendered side-by-side: _VoiceButton (TTS output) and _MicButton (STT input + router).
  Problem: Users cannot distinguish input from output.
  Severity: Critical UX / release-blocking.

- BUG-4 — _MicButton navigates away from Smart Coach Screen mid-session
  File: lib/features/home/ui/smart_coach_screen.dart
  All routing cases in _routeVoiceCommand navigate away without review.
  Severity: High.

3. High-Risk UX Problems
- UX-1 — "SPEAK" label is overloaded (input vs output)
  The TTS output button and the STT input button both use the label "SPEAK".
- UX-2 — _MicButton is not a simple dictation button
  It captures speech, parses it as a voice command, speaks a confirmation, and may navigate away.
- UX-3 — No visual indicator of which button does what
  The buttons are small and inline, and the same label makes them confusing.
- UX-4 — SI Console has no mic button despite STT infrastructure being present
  The STT controller exists but is not wired into the SI Console UI.
- UX-5 — The same label is used for different features across screens
  Smart Coach uses SPEAK for mic input and TTS output; the SI Console uses SPEAK for TTS output only.

4. Nexus Routing Risks
- RISK-1 — showBriefing intent -> flow.toNexus() (CONFIRMED, HIGH)
  File: lib/features/home/ui/smart_coach_screen.dart
  Parser file: lib/state/providers/voice_command_provider.dart
  Trigger: Speech containing "briefing" or similar phrases.
  Confidence: High.
  Risk: STT false positives or user phrases can trigger unexpected navigation.

- RISK-2 — Any stale transcript re-trigger (MEDIUM)
  File: lib/state/controllers/voice_controller.dart
  Risk: A previous transcript could be re-routed if a new session is interrupted or fails.

- RISK-3 — SI Console Back button uses toNexus() (INTENTIONAL, LOW)
  File: lib/features/si_console/ui/si_console_screen.dart
  This one is intentional, not a bug.

8. Permission Findings
- Android manifest includes RECORD_AUDIO permission.
- Runtime permission handling is present before listening starts.
- Permission denial is handled with a SnackBar.
- iOS permission descriptions were not surfaced in this audit and should be verified if iOS is a target.

9. Naming / Architecture Findings
- _MicButton is confusing because it is not just a mic; it is a full voice-command router.
- _VoiceButton is ambiguous because it is purely TTS output but shares the generic "SPEAK" label.
- VoiceService is ambiguous because it is TTS only; a TtsService name would be clearer.
- The voice-command routing logic is embedded in the UI widget and should be extracted for better separation.

10. Test Coverage Gaps
- No tests were found for mic-button behavior, no-accidental-Nexus routing, permission-denied handling, or TTS/STT separation.
- Recommended later tests include:
  - Mic tap does not navigate to Nexus for non-command phrases
  - showBriefing intent routes to Nexus only when intended
  - TTS output button does not navigate
  - Permission denied shows the correct UI and no crash
  - STT start/stop state behaves correctly

11. Recommended Fix Plan
- Phase A: Stop accidental Nexus navigation
  Guard any voice-command navigation path and add an explicit confirmation step before navigating to Nexus or other screens.
- Phase B: Separate STT and TTS actions
  Rename labels, icons, and dialog wording so that mic input and speech output are visibly distinct.
- Phase C: Rename labels/icons safely
  Replace generic "SPEAK" labels with "READ ALOUD" for TTS and "VOICE CMD" or "MIC" for input.
- Phase D: Fix permissions and state handling
  Re-check permission status before each attempt and clear stale transcript state safely.
- Phase E: Clean large/audio assets
  Compress or replace WAV audio and verify whether the large image assets are really needed.
- Phase F: Add tests
  Cover the critical voice navigation and permission paths.
